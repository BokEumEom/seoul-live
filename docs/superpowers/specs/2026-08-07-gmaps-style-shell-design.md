# Google Maps 스타일 셸 개편 설계

상태: 설계 확정
선행 문서: [2026-08-07-map-home-redesign-design.md](./2026-08-07-map-home-redesign-design.md)
참고: 「서울 인파레이더」 <https://gjdong.vercel.app/crowd> (2026-08-07 재조회)

## 1. 왜 다시 고치나

지도 홈 개편을 마친 직후 사용자가 **"UI/UX가 서울 인파레이더와 너무 유사하다"** 고 지적했다. 조사해보니 표면의 문제가 아니었다.

| 겹치는 것 | 확인 |
| --- | --- |
| 지도 + 하단 목록 + 드래그 분할 | 개편 설계 §2.2가 레퍼런스에서 확인하고 채택했다고 명시 |
| 「내 주변」을 탭에서 버튼으로 흡수 | 개편 설계 §2.3이 "레퍼런스도 같은 판단을 했다"고 적었다 |
| 목적 프리셋 **아이와 나들이 / 데이트 / 지금 핫플** | 세 개가 그대로 같다. 우리 프리셋 설계(2026-08-06)가 레퍼런스 조사(08-07)보다 앞서므로 베낀 것은 아니지만, **결과가 같아 차별점 역할을 못 한다** |

즉 우리는 **같은 데이터로 같은 질문("지금 어디가 붐비나")에 답하면서 같은 화면 구조**를 골랐다. 색이나 여백을 바꿔서는 해소되지 않는다.

사용자가 정한 방향은 두 가지다.

1. **지도와 마커가 기본, 하단에 리스트** — 구조는 유지한다
2. **Google Maps 모바일 앱 스타일** — 관용구를 그쪽으로 통일한다

### 이 문서가 다루는 것

셸(shell)과 탐색 구조, 그리고 상세 화면의 정보량이다. 도메인 로직은 건드리지 않는다.

### 다루지 않는 것

| 항목 | 이유 |
| --- | --- |
| 지도 위 시간 스크러버 | §2.7에서 기각. Google Maps 관용구에 없고, 목업 예측으로는 값어치를 검증할 수 없다 |
| 추천 피드를 홈으로 | 30곳으로는 피드가 바닥난다. 121곳 확장이 선행 조건이고 그건 활용갤러리 등록에 막혀 있다 |
| 명소 121곳 확장 | 위와 같음. 이 문서의 결정은 30곳에서도 121곳에서도 성립한다 |
| 실데이터 전환 | 인증키가 없다 |

## 2. 결정과 근거

### 2.1 지도는 배경이고 시트가 그 위에 뜬다

**`SplitPane`(공간 분할)을 `BottomSheet`(오버레이)로 바꾼다.**

지금은 지도와 목록이 세로 공간을 나눠 갖는다(기본 35 : 65). Google Maps는 지도가 뷰포트를 꽉 채우고 시트가 그 위를 덮는다. 시트를 내리면 지도가 온전히 다 보인다.

분할이 나쁜 이유는 **지도가 항상 잘려 있다**는 것이다. 기본값 35%에서 지도는 띠에 가깝고, 명소를 눌러 상세를 열면 그 띠는 아무 일도 하지 않는 장식이 된다. 오버레이는 같은 손잡이 제스처로 지도를 100%까지 열어준다.

3단 스냅을 유지하되 의미를 바꾼다.

| 단계 | 높이 | 내용 |
| --- | --- | --- |
| peek | 16% | 요약 스트립 + 목록 첫 항목. 지도가 주인공 |
| half | 46% (기본) | 목록 |
| full | 92% | 상세 또는 오늘의 서울 |

완전히 0이나 100으로 접지 않는 이유는 기존 설계 §2.2와 같다 — 한쪽이 사라지면 되돌릴 손잡이도 같이 사라진다.

**검색 바와 필터 칩이 지도 위로 떠오른다.** 지금은 시트 위쪽에 얹혀 세로 공간을 먹는데, Google Maps처럼 지도 위에 그림자를 두고 띄우면 시트가 그만큼 넓어진다.

### 2.2 하단 탭바를 없앤다

**탭 셋(지도·즐겨찾기·더보기)을 전부 없애고 단일 화면으로 만든다.**

탭바는 서로 대등한 목적지가 여럿일 때 쓰는 물건이다. 그 기준으로 둘 다 자격이 없다.

- **즐겨찾기** — 목적지가 아니라 지도의 부분집합이다. 담는 곳은 보통 1~3곳이다
- **오늘의 서울** — 목적지에 가깝지만 하루에 한 번 열릴까 말까다

그리고 오버레이 시트를 채택한 이상 **세로 공간이 가장 귀한 자원**이 됐다. 탭바 3.5rem은 시트를 full로 올린 상태에서도 계속 깎인다. 저빈도 앱(주말 나들이 전 한 번)에 상시 3칸은 과하다.

### 2.3 즐겨찾기는 필터 칩이 된다

프리셋 칩 줄 맨 앞에 **「★ 내 장소 N」** 칩을 둔다. 누르면 지도와 목록에 담아둔 곳만 남는다.

탭보다 나은 이유는 **지도 맥락이 유지된다**는 것이다. 지금 구조에서는 즐겨찾기 탭에 가면 지도가 사라진다. 그런데 실제로 답하고 싶은 질문은 "내가 찜한 데 중에 **지금** 한산한 곳"이고, 이건 다른 곳들과 나란히 봐야 답이 나온다. 칩으로 두면 프리셋과 같은 필터 체계 안에 들어온다.

칩은 다른 프리셋과 배타적이다 — 하나를 고르면 나머지가 해제된다. 「내 장소 ∩ 아이와 나들이」 같은 교집합은 30곳 규모에서 결과가 0이 되기 쉽다.

개수가 0이면 비활성이다. 프리셋 칩의 기존 규칙과 같다.

### 2.4 오늘의 서울은 시트 상단 요약 스트립이 된다

시트 맨 위에 한 줄을 고정한다.

```
📊 30곳 중 붐빔 7곳                    ›
⚠️ 재난문자 1건 · 30곳 중 붐빔 7곳      ›   ← 재난문자가 있을 때
```

누르면 시트가 full로 올라가며 기존 「오늘의 서울」 전체(분포·붐빔/여유 TOP·카테고리 평균·추천·출처)가 열린다.

**스트립이 탭보다 더 발견된다.** 탭은 눌러야 보이지만 스트립은 시트를 열 때마다 눈에 들어온다. 그리고 재난문자가 있을 때만 색을 바꿔 시선을 끌 수 있다 — 탭 배지로는 "무엇이" 있는지 알 수 없다.

스트립은 한 줄을 넘지 않는다. 목록 위에 큰 카드를 올리면 half 단계에서 명소가 한 곳도 안 보인다.

### 2.5 목록을 카드에서 구분선으로

| | 현재 | 변경 |
| --- | --- | --- |
| 명소 이름 | `text-headline-sm` 20px/600 | `text-body-md` 16px + `font-semibold` |
| 부가 정보 | `text-label-md` 14px | `text-label-sm` 12px |
| 행 높이 | `min-h-16` (64px) | `min-h-12` (48px) |
| 행 사이 | 카드 테두리 + `gap-3` (12px) | 구분선 1px |
| **행 간격 합계** | **76px** | **56px** |

half 단계에서 보이는 행이 **약 4.3행 → 5.9행**으로 는다. (390×844 기준: 시트 높이 388px에서 손잡이 18px과 요약 스트립 약 40px을 빼면 목록에 330px이 남는다. 검색 바와 칩은 지도 위로 나갔으므로 시트 예산에서 빠진다.)

20px/600은 제목 크기다. 목록의 모든 행이 제목 크기면 위계가 없어지고, 시트라는 좁은 창에서는 스크롤만 길어진다. 터치 타깃 48px은 지킨다.

카드를 버리는 이유는 밀도만이 아니다. 테두리 있는 카드가 세로로 쌓인 형태는 레퍼런스와 겹치는 인상의 큰 부분이고, 구분선 목록이 Google Maps의 관용구다.

### 2.6 상세를 인구 구성까지 확장한다 — 추가 호출 0

사용자 요구는 "자세히 보기는 인파레이더와 같은 정보를 동일하게"다. 확인해보니 **이미 받고 있는 응답에 안 쓰는 필드가 많다.**

`citydata_ppltn` (혼잡도와 같은 응답, 지금 12개 필드를 버리는 중):

| 필드 | 내용 |
| --- | --- |
| `MALE_PPLTN_RATE` · `FEMALE_PPLTN_RATE` | 남녀 비율 |
| `PPLTN_RATE_0` ~ `PPLTN_RATE_70` | 연령대 8단계 비율 |
| `RESNT_PPLTN_RATE` · `NON_RESNT_PPLTN_RATE` | 상주 / 비상주 비율 |

`citydata` (도시 정보와 같은 응답): `ROAD_TRAFFIC_STTS`(도로소통), `ACDNT_CNTRL_STTS`(사고통제), `SUB_STTS`(지하철), `BUS_STN_STTS`(버스), `CHARGER_STTS`(전기차충전소), `LIVE_CMRCL_STTS`(상권), `LIVE_YNA_NEWS`(연합뉴스).

**상주/비상주 비율에 특히 값이 있다.** 비상주가 높으면 외지인이 몰린 곳이고 낮으면 동네 생활권이다. 같은 "보통"이라도 성격이 전혀 다른데 지금은 구분할 방법이 없다.

#### 스키마 전략 — 새 필드는 전부 선택적이다

`schema.ts`는 필수 필드 + 정규식 검증으로 **엄격하게** 파싱한다. 혼잡도는 값이 곧 화면의 존재 이유라 틀린 값을 보여주느니 실패해야 하기 때문이다(AGENTS.md).

**인구 구성 필드를 같은 엄격함으로 추가하면 안 된다.** 비율 필드 하나가 비어 오는 순간 혼잡도까지 통째로 날아간다. 부가 정보 때문에 본체를 잃는 것은 `cityInfoSchema.ts`가 관대한 파싱을 하는 이유와 정확히 같은 상황이다.

따라서 **새 필드는 전부 `optional().nullable()`로 붙이고, 파싱 실패는 `null`로 떨어뜨린다.** 값이 없으면 그 섹션만 렌더하지 않는다. 혼잡도·예측·인구 범위는 지금의 엄격함을 그대로 유지한다.

한 응답 안에서 필드마다 엄격함이 다른 셈인데, 기준은 일관된다 — **화면의 존재 이유인 값은 엄격하게, 없어도 화면이 서는 값은 관대하게.**

#### 상세 구성 (Google Maps 장소 카드 순서)

1. **히어로** — 이름, 카테고리·거리·도보 시간, 혼잡도 배지
2. **액션 행** — 경로 / 저장 / 공유 (Google Maps의 Directions·Save·Share 자리)
3. **현재 상태** — 안내 문구, 추정 인구 범위, 갱신 시각
4. **시간대별 예상** — §2.7
5. **지금 누가 있나** — 남녀 비율, 연령대 막대, 상주/비상주
6. **이곳의 도시 정보** (접이식) — 도로소통 · 주차 · 따릉이 · 날씨 · 문화행사 · 재난문자
7. **근처 쾌적한 장소**

즐겨찾기 별은 히어로 옆이 아니라 **액션 행의 「저장」**으로 옮긴다. Google Maps의 자리이고, 별 아이콘 채움 상태가 테스트로 안 덮이던 문제(STATE.md)도 라벨 있는 버튼이 되면서 사라진다.

**접이식 지연 조회는 그대로 유지한다.** 도시 정보는 접힌 채로 시작하고 펼칠 때만 `useCityInfo`를 켠다. 쿼터를 지키는 자리다.

### 2.7 시간 축은 상세 안에 둔다

**「시간대별 예상」 막대그래프**로 상세에 넣는다. 지도 위 스크러버는 넣지 않는다.

Google Maps에는 장소 상세에 **「인기 시간대」 막대그래프**가 있다. 우리 `FCST_PPLTN`은 그것의 실시간판이라 같은 자리에 더 강한 데이터가 들어가는 셈이고, 사용자에게 학습 비용이 없다.

**기각한 안: 지도 위 시간 스크러버.** 띠를 끌면 마커가 그 시각의 예측으로 다시 칠해지는 안을 검토했다. 예측 데이터가 없으면 만들 수 없는 화면이라 차별점으로는 가장 강하다. 기각 이유는 둘이다.

1. Google Maps 관용구에 없다. 스타일을 그쪽으로 통일하기로 한 결정과 충돌한다
2. **목업으로는 값어치를 검증할 수 없다.** 목업 예측은 우리가 해시로 만든 값이라 시간대별로 갈리는 것이 당연하다. 실데이터에서 대부분 명소의 예측이 평평하게 나오면 띠가 온통 같은 색이 되어 아무 값도 못 한다. 인증키가 나온 뒤 실제 예측 분포를 보고 다시 판단한다

## 3. 그래서 차별화가 되나 — 정직한 점검

이 개편으로 레퍼런스와 갈리는 것과 여전히 같은 것을 나눠 적는다. 나중에 "차별화했다고 하지 않았나"가 나오지 않도록.

**갈리는 것**

- 셸 관용구가 다르다 — 오버레이 시트 + 떠 있는 검색/칩 + 탭바 없음
- 상세 정보량이 다르다 — 인구 구성(성별·연령·상주비율)과 도로소통까지
- 목록 밀도와 형태가 다르다 — 구분선, 16px

**여전히 같은 것**

- **핵심 질문이 같다.** "지금 어디가 붐비나"에 지도+마커로 답한다
- **목적 프리셋 3종이 같다.** 이름까지 같다
- 레퍼런스는 121곳, 우리는 30곳이라 오히려 커버리지가 좁다

**결론:** 이 개편은 유사성을 **줄이지만 없애지 못한다.** 질문 자체를 바꾸는 것(시간 축을 주인공으로)이 유일한 근본 해법인데, 그건 §2.7의 이유로 실데이터 확보 후로 미뤘다. 프리셋 이름 3종은 지금이라도 바꿀 수 있으나 이번 범위 밖으로 둔다 — 사용자 결정이 필요하다.

| `home/AreaDetail.tsx` | 액션 행 추가, 인구 구성 섹션 추가, 별 → 「저장」 |

`focusArea`가 없어진다 — 즐겨찾기·오늘의 서울이 별도 화면이 아니게 되면서 "홈으로 보내 상세를 연다"는 경로 자체가 사라진다. 시트 안에서 바로 상세로 바뀐다.

## 5. 실패 경로

| 상황 | 동작 |
| --- | --- |
| 지도 키 없음 / 스크립트 실패 | 지도 자리에 안내를 깔고 **시트를 half로 고정**한다. 검색·목록·상세·필터는 전부 정상 동작해야 한다. 지도가 배경이 되면서 이 경로가 더 중요해졌다 |
| 혼잡도 조회 실패 | 시트에 에러와 재시도. 지도는 마커 없이 남는다 |
| 인구 구성 필드 없음/이상 | 해당 섹션만 렌더하지 않는다. 혼잡도·예측은 그대로 |
| 도시 정보 실패 | 접이식 영역 안에만 에러. 위쪽은 그대로 |
| 즐겨찾기 0곳 | 「★ 내 장소」 칩이 비활성(0)이 된다. 별도 빈 화면은 없어진다 |

## 6. 미해결 가정

- **시트 드래그와 지도 팬 제스처의 충돌.** 오버레이가 되면서 시트 손잡이 바로 아래가 지도다. 손잡이를 잡으려다 지도가 팬되는지는 실기기로만 안다. `touch-action:none`과 포인터 캡처로 막았다고 가정한다
- **시트 안 스크롤과 시트 드래그의 충돌.** full 단계에서 상세를 위로 스크롤할 때 시트가 따라 내려가면 안 된다. 손잡이에서만 드래그를 받는 것으로 1차 방어하되, 실기기 확인이 필요하다
- **인구 구성 필드의 실제 형태.** `"52.3"`인지 `"52"`인지, 합이 100인지 모른다. 선택적 파싱이라 틀려도 화면이 깨지지는 않지만 표시 형식은 실응답을 봐야 확정된다
- **예측이 실제로 시간대별로 갈리는지.** §2.7의 기각 근거이자 「시간대별 예상」 자체의 전제다. 평평하면 이 섹션도 값이 줄어든다
- **iOS 안전 영역.** 시트가 화면 바닥에 붙으므로 홈 인디케이터와 겹치는지 확인해야 한다

## 7. 검증

- 목록 행 간격이 56px이고 half에서 5행 이상 보인다
- 시트 3단 스냅이 동작하고, 손잡이를 누르기만 하면 아무 일도 없다
- 명소를 누르면 시트가 full로 올라가며 상세가 뜨고 **지도는 사라지지 않는다**
- 「★ 내 장소」 칩이 즐겨찾기만 남긴다. 0곳이면 비활성
- 요약 스트립을 누르면 오늘의 서울이 열린다. 재난문자가 있으면 스트립 색이 바뀐다
- 인구 구성 필드를 응답에서 빼도 혼잡도가 살아 있다
- 지도 키를 지워도 검색·목록·상세가 동작한다
- `npm test` · `npx tsc -b` · `npm run lint` · `npm run build:vite` 통과
