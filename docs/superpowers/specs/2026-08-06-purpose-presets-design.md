## 1. 목표와 범위

지도 화면에 「아이와 나들이 / 데이트 / 지금 핫플」 세 칩을 올려, 상황에 맞는 명소만 남긴다. PLAN.md 2차의 「목적 프리셋」 항목이다.

카테고리 필터가 "무엇인가"로 거른다면 프리셋은 "지금 무엇을 하려는가"로 거른다. PLAN.md의 설계 원칙 중 **목적 중심의 UI** — "데이터를 나열하는 게 아니라 상황별 프리셋으로 의사결정을 돕는다" — 가 이 기능이다.

### 이 문서가 다루는 것

| 항목 | 내용 |
|---|---|
| 프리셋 3종 | 카테고리와 실시간 혼잡도를 조합한 술어 |
| 칩 UI | 지도 상단, 해당 개수 표시, 0이면 비활성 |
| 필터링 | 마커를 거르고, 선택 상태를 정리 |

### 범위 밖 (근거 포함)

| 제외 항목 | 근거 |
|---|---|

| 프리셋 커스터마이즈 | 사용자가 조건을 편집하는 기능. 세 개가 실제로 쓰이는지부터 본다 |
| 「내 주변」에 적용 | 시안(`stitch_ui/_2`)이 그 화면에 카테고리 칩을 그렸다. §2.2 참고 |
| 프리셋별 정렬 변경 | 예: 「지금 핫플」을 혼잡도순으로. 지도에는 정렬이 없다 |

## 2. 결정과 근거

### 2.1 카테고리와 혼잡도를 함께 쓴다

프리셋을 카테고리 여러 개의 별칭으로만 만들 수도 있었다. 그러면 구현이 단순하지만 **결과가 하루 종일 고정**되고, 「내 주변」의 카테고리 필터와 사실상 같은 기능이 된다. 실시간 인구 데이터를 쓰는 앱에서 목적 필터가 실시간이 아니면 이름값을 못 한다.

반대로 혼잡도만 쓰면 "한산한 곳 / 붐비는 곳"이 되어 장소 성격과 무관해지고, 이름이 프리셋이 아니라 혼잡도 필터가 된다.

둘을 조합한다.

### 2.2 지도 화면에만 둔다

시안이 이미 나눠 놓았다 — `stitch_ui/_1`(지도)에는 목적 프리셋, `stitch_ui/_2`(내 주변)에는 카테고리 칩이다. 두 화면이 서로 다른 축으로 거르므로 역할이 겹치지 않는다.

「내 주변」에 프리셋을 더하면 필터 줄이 두 개가 되고, "공원 + 데이트"처럼 둘을 동시에 고를 때 어느 쪽이 이기는지 규칙을 또 정해야 한다. 카테고리 칩을 프리셋으로 **교체**하는 안은 "공원만 보기" 같은 단순 탐색을 없애고 이미 테스트된 기능을 버린다.

### 2.3 칩에 개수를 표시하고 0이면 비활성

프리셋이 실시간 혼잡도를 쓰면 **결과가 0곳이 될 수 있다.** 주말 오후에 공원 10곳이 전부 붐비면 「아이와 나들이」가 비고, 새벽에는 붐비는 곳이 없어 「지금 핫플」이 빈다. 정적 카테고리 필터에는 없던 상황이다.

칩에 개수를 미리 달면 누르기 전에 알 수 있다. "눌렀는데 아무 일도 안 일어났다"는 순간이 생기지 않고, 지금 어떤 목적이 가능한지가 한눈에 보인다. 실시간성이 숫자로 드러나는 것은 이 앱의 성격에도 맞는다.

0곳일 때 조건을 조용히 완화하는 안은 기각했다 — 붐비는 공원을 "아이와 가기 좋은 곳"으로 보여주게 된다.

### 2.4 「데이트」에도 혼잡도 조건을 넣는다

브레인스토밍 중 「데이트」는 카테고리만(카페 ∪ 문화재 ∪ 공원)으로 잡혀 있었다. 그러면 카탈로그상 **항상 19곳으로 고정**되어, 옆의 두 칩이 시간대마다 바뀌는 사이에서 혼자 죽은 숫자가 된다. 데이트에 「붐빔」은 실제로 나쁜 조건이기도 하다. `붐빔 아님`을 더해 세 칩이 모두 실시간이 되게 한다.

### 2.5 스냅샷이 없는 명소는 어느 프리셋에도 안 걸린다

조회에 실패한 명소는 혼잡도를 모른다. 모르는 것을 "한산하다"고 말할 수 없다. 지도 전체 보기에서는 회색 "정보 없음" 마커로 남지만(지도 설계 §4.2), 프리셋을 켜면 빠진다.

## 3. 프리셋 정의

```text
아이와 나들이  →  카테고리 = 공원      ∩  혼잡도 ∈ {여유, 보통}
데이트        →  카테고리 ∈ {카페, 문화재, 공원}  ∩  혼잡도 ≠ 붐빔
지금 핫플      →  혼잡도 = 붐빔
```

카탈로그 30곳의 카테고리 분포는 공원 10 / 기타 7 / 문화재 6 / 쇼핑몰 4 / 카페 3이다. 「데이트」의 카테고리 후보는 19곳이고 여기서 붐빔이 빠진다.

`혼잡도 ∈ {여유, 보통}`은 `src/domain/congestion.ts`의 `isUncrowded()`와 같은 범위다. 그 함수를 쓴다 — 같은 판단이 두 곳에 따로 있으면 한쪽만 고쳐지는 날이 온다.

## 4. `src/domain/presets.ts`

프리셋 정의와 필터링을 순수 함수로 둔다. React도 SDK도 모른다.

```ts
export type PresetKey = 'kids' | 'date' | 'hot'

export interface Preset {
  readonly key: PresetKey
  readonly label: string
  readonly matches: (area: NearbyArea) => boolean
}

export const PRESETS: readonly Preset[]

export function filterByPreset(
  areas: readonly NearbyArea[],
  preset: PresetKey | null,
): readonly NearbyArea[]

export function presetCounts(
  areas: readonly NearbyArea[],
): Readonly<Record<PresetKey, number>>
```

`matches`가 프리셋마다 한 줄짜리 술어라 정의가 한눈에 들어온다. **개수 세기와 거르기가 같은 술어를 쓰므로** 칩 숫자와 실제 마커 수가 어긋날 수 없다.

`filterByPreset(areas, null)`은 입력을 그대로 돌려준다 — 호출부가 분기하지 않아도 된다.

### 왜 별도 모듈인가

`buildNearbyList`에 인자를 더하는 안은 기각했다. 그 함수는 이미 카테고리 필터·거리 계산·정렬 세 가지를 하고 있고, 프리셋까지 넣으면 넷이 된다. 「내 주변」은 프리셋을 쓰지 않는데 시그니처만 넓어진다.

`domain/map.ts`에 합치는 안도 기각했다. 그 파일은 **표시 규칙**(줌에 따른 라벨, 마커 변환)이고 프리셋은 **선택 의미**다. 섞으면 "지도 관련 잡동사니" 파일이 된다.

## 5. `src/components/map/PresetFilter.tsx`

```ts
interface Props {
  readonly counts: Readonly<Record<PresetKey, number>>
  readonly value: PresetKey | null
  readonly onChange: (next: PresetKey | null) => void
}
```

- 칩에 `아이와 나들이 3` 형태로 개수를 단다
- 개수가 0이면 `disabled`
- **선택된 칩을 다시 누르면 해제**된다(전체 보기로 복귀). 「전체」 칩을 따로 두지 않는 이유는 지도에서 칩 4개가 상단 공간을 더 먹기 때문이다
- `CategoryFilter`와 같은 `role="tablist"` 패턴을 쓰되 별도 컴포넌트다 — 한쪽은 정적 카테고리, 다른 쪽은 실시간 개수라 props 모양이 다르다

지도 위에 떠 있으므로 `absolute`에 `pointer-events-auto`가 필요하다. `RecenterButton`과 같은 제약이다.

## 6. `MapScreen` 변경

```ts
const [preset, setPreset] = useState<PresetKey | null>(null)

const counts = presetCounts(list)
const visible = filterByPreset(list, preset)
const markers = snapshots.isPending ? [] : toMapMarkers(visible)
```

**개수는 `visible`이 아니라 `list`로 센다.** 걸러진 목록으로 세면 프리셋을 하나 고르는 순간 나머지 두 칩이 0이 되어 비활성으로 굳고, 다른 목적으로 갈아탈 방법이 사라진다. 칩의 숫자는 언제나 "전체 30곳 중 이 조건에 맞는 수"다.

**현재 위치 마커는 프리셋의 영향을 받지 않는다.** 명소 마커와 별개로 렌더되며, 어떤 목적으로 거르든 내가 어디 있는지는 그대로 보여야 한다.

### 선택 상태를 정리해야 한다

강남역 시트를 열어둔 채 「아이와 나들이」를 누르면 강남역은 마커에서 빠지는데 시트는 남는다. 지도에 없는 명소의 요약이 떠 있는 상태다.

```ts
function handlePreset(next: PresetKey | null): void {
  setPreset(next)
  setSelectedName(null)
}
```

프리셋을 바꿀 때 선택을 해제한다. 살아남은 명소만 골라 유지하는 방법도 있지만, 규칙이 늘고 사용자에게 이득이 없다 — 프리셋을 바꾼 사람은 다시 고를 준비가 돼 있다.

### 로딩 중

`snapshots.isPending`이면 `list`가 비어 개수가 전부 0이 되고 칩이 모두 비활성이 된다. 데이터가 없으니 정확한 표시다. 별도 처리가 필요 없다.

변이 확인 — 「데이트」의 붐빔 제외를 지우면 개수가 19로 굳는지, `setSelectedName(null)`을 빼면 시트가 남는지. 둘 다 실패해야 한다.

## 8. 열려 있는 질문

- **프리셋 이름이 실제 의도와 맞는지는 써봐야 안다.** 「데이트」가 카페·문화재·공원인 것은 가정이다. 사용자가 쇼핑몰을 기대할 수도 있다. 세 개가 실제로 쓰이는지, 어떤 조건이 기대와 다른지는 실기기 사용에서 나온다.
- **「지금 핫플」의 정의가 좁을 수 있다.** 지금은 `붐빔`만인데 `약간 붐빔`까지 넣으면 개수가 안정된다. 실데이터에서 `붐빔`이 하루 중 몇 시간이나 나오는지 보고 정한다 — 목업으로는 판단할 수 없다.
