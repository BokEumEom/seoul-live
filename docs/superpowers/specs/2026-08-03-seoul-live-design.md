# 서울 라이브 (Seoul Live) — 앱인토스 미니앱 설계

작성일: 2026-08-03
상태: 1차 설계 확정

## 1. 목표와 범위

서울시 실시간 도시데이터를 활용해, 나가기 전에 목적지가 붐비는지 확인할 수 있는 토스 미니앱을 만든다.

### 1차 범위 (이 문서가 다루는 것)

| 화면 | 내용 |
|---|---|
| 내 주변 | 현재 위치 기준 명소 목록, 혼잡도 배지, 거리순 정렬, 카테고리 필터, "가까우면서 여유로운 곳" 추천 |
| 혼잡예보 | 명소 상세, 현재 혼잡 상태와 메시지, 시간별 예측 차트, 한산해지는 시각 안내, 길찾기/공유 |

하단 탭은 시안대로 4개(지도·내 주변·혼잡예보·더보기)를 노출하되, 지도와 더보기는 비활성 상태로 둔다.

### 1차에서 제외 (근거 포함)

| 제외 항목 | 근거 |
|---|---|
| 지도 화면 | 카카오/네이버 지도 키 발급과 도메인 등록이 선행돼야 함. 리스트만으로 핵심 가치가 성립함 |
| 도시정보(더보기) 화면 | 주차·따릉이·도로소통·문화행사·재난문자 등 별도 API 5종이 추가로 필요 |
| 요일×시간 히트맵 | 서울 API는 현재와 예측만 제공. 과거 데이터 누적용 저장소가 필요 |
| 어제 대비 비교 | 위와 동일한 이유 |
| CCTV 영상 | 별도 API이며 웹뷰 재생 제약 검증이 필요 |

## 2. 핵심 제약

설계를 좌우하는 사실들이다. 모두 직접 확인했다.

### 2.1 서울 OpenAPI는 HTTPS를 지원하지 않는다

`openapi.seoul.go.kr`은 8088 포트의 평문 HTTP만 열려 있다. 80·443 포트는 닫혀 있고, 8088로 TLS 핸드셰이크를 시도하면 실패한다.

토스 미니앱은 HTTPS로 로드되므로 브라우저가 mixed content로 요청을 차단한다. 클라이언트에서 직접 호출하는 경로는 존재하지 않는다. **HTTPS 중계 서버가 동작의 전제 조건이다.**

### 2.2 하루 1,000회 호출 제한

일반인증키는 하루 1,000회로 제한된다. 활용갤러리에 등록하면 해제된다.

`citydata_ppltn`은 `AREA_NM`이 필수 파라미터라 **명소 1곳당 1회 호출**이 든다. 파라미터를 생략하면 500 에러가 난다.

| 명소 수 | 갱신 주기 | 하루 호출량 | 1,000회 대비 |
|---|---|---|---|
| 121곳 | 5분 | 34,848회 | 35배 초과 |
| 121곳 | 1시간 | 2,904회 | 2.9배 초과 |
| 30곳 | 10분 | 4,320회 | 4.3배 초과 |
| 30곳 | 1시간 | 720회 | 통과 |

**결론**: 갤러리 등록 전에는 명소 30곳 / 1시간 갱신으로 운영한다. 등록 후 121곳 / 5분으로 확장한다. 이 값은 설정 상수 하나로 바꿀 수 있게 만든다.

클라이언트 캐시로는 이 문제를 풀 수 없다. 캐시가 기기마다 따로 존재하므로 사용자 수에 비례해 호출량이 늘어난다. **서버 측 공용 캐시가 필요하다.**

### 2.3 API 응답에 좌표가 없다

`citydata_ppltn` 응답 필드는 `AREA_NM`, `AREA_CD`, `AREA_CONGEST_LVL`, `AREA_CONGEST_MSG`, 인구 추정치와 연령·성별 비율, `PPLTN_TIME`, `FCST_PPLTN`이다. 위경도는 없다.

거리순 정렬과 "내 주변"이 성립하려면 **명소 좌표를 담은 정적 카탈로그를 직접 관리**해야 한다. 카테고리 필터(공원·쇼핑몰·카페·문화재)에 쓸 분류도 API가 주지 않으므로 같은 카탈로그에 넣는다.

### 2.4 sample 키로는 실데이터 검증이 불가능하다

인증키 자리에 `sample`을 넣으면 지역명과 무관하게 항상 광화문·덕수궁 응답만 돌아온다. 강남역·홍대입구역·여의도한강공원으로 호출해도 결과가 같다.

따라서 개발 초기에는 목업 데이터를 쓰고, 인증키 발급 후 실데이터로 전환한다. 목업은 실제 응답 스키마와 동일한 형태로 만들어 전환 시 코드 변경이 없도록 한다.

## 3. 아키텍처

```
┌─────────────────────────────────────────┐
│  토스 웹뷰 (HTTPS)                        │
│  React 19 + Vite + TanStack Query        │
└───────────────┬─────────────────────────┘
                │ HTTPS
┌───────────────▼─────────────────────────┐
│  Vercel Function  api/citydata.ts        │
│  - 인증키 주입 (서버 환경변수)              │
│  - 응답 정규화                             │
│  - Cache-Control: s-maxage               │
└───────────────┬─────────────────────────┘
                │ HTTP (서버→서버, 제약 없음)
┌───────────────▼─────────────────────────┐
│  openapi.seoul.go.kr:8088                │
└─────────────────────────────────────────┘
```

### 3.1 프록시가 얇은 이유

KV·Redis·DB를 쓰지 않는다. `Cache-Control: s-maxage=<TTL>, stale-while-revalidate=<TTL*2>` 헤더만 내려주면 Vercel CDN이 엣지에서 캐싱한다. 사용자가 1명이든 1만 명이든 서울 API 호출량은 갱신 주기에 의해서만 결정된다.

**TTL은 2.2의 쿼터 계산과 직결되므로 상수 하나로 관리한다.**

| 단계 | 명소 수 | TTL | 하루 호출량 |
|---|---|---|---|
| 갤러리 등록 전 | 30곳 | 3600초 (1시간) | 720회 — 한도 내 |
| 갤러리 등록 후 | 121곳 | 300초 (5분) | 34,848회 — 제한 없음 |

`CACHE_TTL_SECONDS` 환경변수로 두어 갤러리 등록 시 재배포 없이 전환한다.

인증키는 `SEOUL_API_KEY` 환경변수로만 읽고 앱 번들에는 포함하지 않는다.

### 3.2 두 캐시 계층의 역할 분담

| 계층 | 담당 | 담당하지 않는 것 |
|---|---|---|
| Vercel CDN (s-maxage) | 서울 API 쿼터 방어. 전 사용자 공유 | UI 상태 |
| TanStack Query | 로딩·에러 상태, 화면 전환 시 재사용, 포커스 복귀 시 재검증 | 쿼터 방어 |

### 3.3 프록시 엔드포인트

```
GET /api/citydata?area=<AREA_NM>       단일 명소 상세  → 혼잡예보 화면
GET /api/citydata/bulk?areas=a,b,c     복수 명소 요약  → 내 주변 화면
```

`bulk`는 서버에서 병렬 호출 후 합쳐 내려준다. 개별 명소 실패는 전체를 실패시키지 않고 해당 항목만 `null`로 표시한다.

## 4. 모듈 구조

파일은 200~400줄을 넘기지 않도록 기능 단위로 나눈다.

```
api/
  citydata.ts              단일 명소 프록시
  citydata/bulk.ts         복수 명소 프록시
  _lib/
    seoul-client.ts        서울 API 호출 + 인증키 주입
    normalize.ts           원본 응답 → 앱 도메인 모델 변환

src/
  domain/
    congestion.ts          혼잡도 4단계 정의, 색상/라벨 매핑
    area.ts                명소 도메인 타입
    distance.ts            하버사인 거리 계산
  data/
    areas.ts               명소 정적 카탈로그 (좌표·카테고리)
    schema.ts              zod 응답 스키마
    queries.ts             TanStack Query 훅
    mock.ts                목업 데이터 (인증키 발급 전용)
  hooks/
    useCurrentLocation.ts  토스 위치 권한 + 좌표 획득
    useNearbyAreas.ts      거리 계산 + 정렬 + 필터
  components/
    common/                Badge, Chip, Card, Skeleton, ErrorState
    nearby/                내 주변 화면 구성 요소
    forecast/              혼잡예보 화면 구성 요소
    layout/                TopAppBar, BottomTabBar
  screens/
    NearbyScreen.tsx
    ForecastScreen.tsx
  styles/
    tokens.css             DESIGN.md 토큰
  App.tsx
  main.tsx
```

### 4.1 각 모듈의 경계

- `domain/`은 React를 모른다. 순수 함수와 타입만 둔다. 단위 테스트가 쉽다.
- `data/`는 네트워크와 스키마를 담당한다. 컴포넌트는 `queries.ts`의 훅만 쓰고 fetch를 직접 호출하지 않는다.
- `components/`는 props만 받는다. 데이터 페칭은 `screens/`에서 한다.
- 목업↔실데이터 전환은 `queries.ts` 한 곳에서만 일어난다.

## 5. 데이터 모델

### 5.1 명소 카탈로그 (`data/areas.ts`)

```typescript
interface AreaCatalogEntry {
  readonly code: string        // POI009
  readonly name: string        // 광화문·덕수궁 (API 호출 키)
  readonly lat: number
  readonly lng: number
  readonly category: AreaCategory
}

type AreaCategory = '공원' | '쇼핑몰' | '카페' | '문화재' | '관광특구' | '기타'
```

1차에는 30곳을 수록한다. 좌표는 명소 중심점 기준으로 수집한다.

### 5.2 혼잡도 (`domain/congestion.ts`)

서울 API는 4단계를 준다. 시안은 3색 체계다. 다음과 같이 매핑한다.

| API 값 | 앱 표기 | 색상 |
|---|---|---|
| 여유 | 여유 | success (초록) |
| 보통 | 보통 | warning (노랑) |
| 약간 붐빔 | 약간 붐빔 | warning-strong (주황) |
| 붐빔 | 붐빔 | danger (빨강) |

4단계를 그대로 살린다. 시안의 3색을 4색으로 확장하되 색상 계열은 유지해 학습 비용을 없앤다.

### 5.3 응답 검증

zod로 프록시 응답을 검증한다. 서울 API가 문자열로 주는 숫자 필드(`AREA_PPLTN_MIN` 등)는 스키마 단계에서 숫자로 변환한다. 검증 실패 시 해당 명소만 에러 상태로 표시하고 나머지는 정상 렌더링한다.

## 6. 화면 사양

### 6.1 내 주변 (`NearbyScreen`)

구성 순서는 시안 `_2`를 따른다.

1. TopAppBar — 타이틀, 검색 버튼
2. 헤드라인 — "내 주변 명소" / "현재 위치 기반 실시간 혼잡도 정보"
3. 카테고리 필터 칩 — 전체·공원·쇼핑몰·카페·문화재
4. 추천 캐러셀 — "가까우면서 여유로운 곳 추천". 거리와 혼잡도를 함께 고려한 점수로 상위 항목을 고른다
5. 거리순 리스트 — 명소명, 거리, 카테고리·지역, 혼잡도 배지
6. 현재 위치 재조회 FAB
7. 하단 탭바

**추천 로직**: 도보 30분(2km, 시안의 "800m·도보 12분" 기준인 시속 4km 적용) 이내 명소 중 혼잡도가 여유·보통인 것을 거리 오름차순으로 정렬해 상위 5개를 노출한다. 조건을 만족하는 항목이 없으면 섹션 자체를 숨긴다.

**위치 권한 거부 시**: 거리 관련 UI를 숨기고 혼잡도 낮은 순 정렬로 대체한다. 화면은 정상 동작한다.

### 6.2 혼잡예보 (`ForecastScreen`)

구성 순서는 시안 `_3`을 따르되, 과거 데이터가 필요한 요소는 뺀다.

1. TopAppBar — 뒤로가기, 명소명
2. 현재 상태 카드 — 혼잡도 배지, 상태 문구, `AREA_CONGEST_MSG`, 마지막 업데이트 시각
3. 한산 시간 안내 — `FCST_PPLTN`에서 혼잡도가 여유로 떨어지는 가장 이른 시각을 찾아 "N시엔 여유 예상"으로 표시. 현재가 이미 여유면 숨긴다
4. 시간별 예측 차트 — `FCST_PPLTN` 기반 SVG 라인 차트. 현재 시점 이후 구간은 점선
5. 길찾기 버튼 — 카카오맵·네이버 URL 스킴 연결
6. 공유 버튼

시안의 "어제" 비교선과 요일×시간 히트맵은 데이터 부재로 1차에서 제외한다.

## 7. 에러 처리

| 상황 | 처리 |
|---|---|
| 프록시 응답 실패 | 재시도 버튼이 있는 에러 상태. TanStack Query 재시도 2회 |
| 개별 명소 실패 | 해당 카드만 "정보 없음"으로 표시. 나머지는 정상 |
| 스키마 검증 실패 | 해당 명소를 에러 항목으로 처리. 원인은 서버 로그로만 남긴다 |
| 위치 권한 거부 | 거리 UI 숨기고 혼잡도순 정렬로 대체 |
| 위치 조회 타임아웃 | 10초 후 권한 거부와 동일하게 처리 |
| 서울 API 쿼터 소진 | 프록시가 `stale-while-revalidate`로 직전 캐시를 계속 서빙. 화면에 "갱신 지연" 표시 |
| 네트워크 없음 | `Environment.getNetworkStatus`로 감지해 안내 |

사용자에게 보여주는 메시지에 API 원문 에러나 인증키를 노출하지 않는다.

## 8. 테스트 전략

TDD로 진행한다. 커버리지 80% 이상을 목표로 한다.

| 대상 | 방식 |
|---|---|
| `domain/distance.ts` | 단위 테스트. 알려진 두 좌표 간 거리 검증 |
| `domain/congestion.ts` | 단위 테스트. 4단계 매핑과 미지의 값 처리 |
| `data/schema.ts` | 단위 테스트. 정상·필드누락·타입불일치 응답 |
| `hooks/useNearbyAreas.ts` | 단위 테스트. 정렬·필터·추천 선정 로직 |
| `api/_lib/normalize.ts` | 단위 테스트. 원본→도메인 변환 |
| 화면 | Testing Library. 로딩·정상·에러·권한거부 4가지 상태 |

도구는 Vitest와 Testing Library를 쓴다.

## 11. 선행 작업 (사용자 진행 필요)

1. data.seoul.go.kr 회원가입
2. 일반 인증키 발급 — 서비스별 신청 불필요, 즉시 발급
3. 활용갤러리에 인증키와 함께 앱 등록 — 하루 1,000회 제한 해제. 출시 전까지 완료 필요

## 12. 검증되지 않은 가정

- **토스 웹뷰의 mixed content 정책**: 웹뷰가 HTTPS로 번들을 서빙한다고 가정했다. 만약 로컬 파일 스킴으로 서빙된다면 HTTP 직접 호출이 가능할 수도 있다. 실제 기기 테스트로 확인한다. 다만 쿼터 문제 때문에 프록시는 여전히 필요하므로 설계는 바뀌지 않는다.
- ~~**`AREA_NM` 일괄 조회**: 가능하다면 쿼터 문제가 사라진다.~~ **불가능으로 확정.** 공식 데이터셋 문서가 "한 번에 1개 장소씩만 호출 가능"이라고 명시한다. 명소 1곳당 1회 호출이 확정이므로 서버 측 공용 캐시가 필수다.
- **명소 좌표**: 서울시가 공식 좌표 목록을 제공하는지 미확인. 없으면 직접 수집한다.
