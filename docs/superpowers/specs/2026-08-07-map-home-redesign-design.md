## 1. 목표와 범위

화면 넷(내 주변·지도·혼잡예보·더보기)을 **셋(지도·즐겨찾기·더보기)** 으로 바꾸고, 지도를 홈으로 올린다. 지도 홈이 목록과 상세를 함께 안고, 비워진 「더보기」는 서울 전체 현황으로 다시 채운다.

### 이 문서가 다루는 것

| 항목 | 내용 |
|---|---|
| 지도 홈 | 지도 + 드래그 분할 + 검색 + 프리셋·카테고리 + 목록 + 인플레이스 상세 |
| 즐겨찾기 | 기기 로컬 저장, 저장한 명소만 보는 탭 |
| 오늘의 서울 | 혼잡도 분포, 붐빔·여유 TOP, 카테고리별 평균, 재난문자 모음, 추천, 출처·설정 |
| 카테고리 | 공식 5종으로 교체, 화면 라벨은 사용자 언어 |
| 프리셋 | 카테고리에서 분리해 독립 목적 태그로 |
| 검색 | 명소명 부분일치 |

### 범위 밖 (근거 포함)

| 제외 항목 | 근거 |
|---|---|
| 명소 121곳 확장 | 활용갤러리 등록이 선행 조건. 쿼터가 풀리기 전에는 30곳이 상한 |
| 이력 기반 기능 (요일×시간 히트맵, 어제 대비, N시간 전 대비) | 수집 크론과 저장소가 선행. PLAN.md 4차 |
| CCTV | 별도 API이고 앱인토스 iframe 금지 조항 검토가 따라붙는다 |
| 도로소통·사고통제·지하철·버스·전기차충전소·상권·연합뉴스 | 같은 `citydata` 응답에 있어 추가 호출은 없으나, 이번은 **구조** 변경에 집중한다. 상세에 섹션을 더하는 일이라 구조가 서면 붙이기 쉽다 |
| 주소 검색 | 지오코딩 API가 필요하다. 명소명 검색만 한다 |
| 다도시(제주·부산·강원·인천공항) | 서울 외 지역은 별도 API이고 이 앱의 이름과 범위를 벗어난다 |
| 다크모드·다국어 | 토스 웹뷰의 테마·로케일 정책을 확인하지 않았다 |
| 지도 라이브러리 교체 | 레퍼런스는 Leaflet을 쓰지만 기능 차이가 아니라 구현 선택이다. `@vis.gl/react-google-maps` 채택 근거는 지도 탭 설계 §3에 있고 이번 변경으로 무효가 되지 않는다 |

## 2. 결정과 근거

### 2.1 지도가 홈이고, 상세는 목록 자리에만 들어온다

명소를 누르면 지도는 그대로 두고 아래쪽 목록만 상세로 바뀐다. 지도는 그 명소로 줌인한다.

지금은 상세로 가면 `MapScreen`이 언마운트되면서 카메라와 선택 상태가 서울 전역으로 되돌아간다. STATE.md에 "알고 있지만 아직 안 고친 것"으로 남아 있고, 고치려면 카메라 상태를 `App.tsx`로 끌어올려야 해서 지도 상태가 셸로 새어나간다는 문제가 있었다. **홈이 언마운트되지 않는 구조에서는 이 문제가 사라진다** — 상태를 위로 올리지 않고도 카메라가 보존된다.

상세에는 지금의 「혼잡예보」(현재 상태·시간별 예측·길찾기·공유)에 더해 **지금 「더보기」에 있던 도시 정보**(주차장·따릉이·날씨·대기·문화행사·재난문자)가 내려온다. `citydata`가 장소 단위 API라 명소 상세가 제자리다.

### 2.2 드래그 분할 — 바텀시트를 기각한 이유

지도와 목록 사이에 손잡이를 두고 세로 비율을 사용자가 조절한다. 더블탭으로 초기화한다.

**바텀시트 안(지도 전체화면 + 끌어올리는 시트)을 기각했다.** 앱인토스 심사 체크리스트에 "미니앱에 진입하자마자 바텀시트가 자동으로 나타나지 않아요"가 있다. 상시 레이아웃 시트와 모달 시트는 성격이 다르지만, 심사자가 그 구분을 해준다는 근거가 문서에 없다. 같은 조항 때문에 지도 탭 설계 §2.5에서 시안 `stitch_ui/_1`을 그대로 옮기지 않기로 이미 정한 바 있다. 홈 화면 전체를 확인되지 않은 해석에 걸 이유가 없다.

**고정 분할 안도 기각했다.** 제스처가 없어 가장 안전하지만, 지도 탭인데 지도가 화면의 3분의 1로 고정되고 크게 볼 방법이 없다.

드래그 분할은 레퍼런스에서 실제로 동작하는 것을 확인했고, "지도를 크게"와 "목록을 크게"를 사용자가 직접 고를 수 있어 두 기각안의 문제를 모두 피한다.

구체값은 이렇게 둔다. 지도 높이의 **기본값은 가용 높이의 35%**, 범위는 **15%~75%**다. 손잡이를 놓으면 가장 가까운 스냅(15 / 35 / 75)으로 붙고, 더블탭하면 35%로 돌아온다. 15%는 지도가 띠처럼 남아 "지금 어디를 보고 있나"만 알려주는 상태이고, 75%는 목록이 두어 줄만 남는 상태다. 완전히 0이나 100으로 접히지 않게 하는 이유는 한쪽이 사라지면 되돌릴 손잡이도 같이 사라지기 때문이다.

### 2.3 탭 셋

| 탭 | 내용 |
|---|---|
| 지도 (홈) | 2.1 |
| 즐겨찾기 | 저장한 명소만, 홈 목록과 같은 카드 |
| 더보기 | 「오늘의 서울」 |

즐겨찾기가 비어 있으면 "지도에서 ☆를 눌러 담아보세요"로 안내하고, 홈으로 가는 버튼을 둔다. 빈 화면만 보여주면 이 탭이 고장 난 것으로 읽힌다.

「내 주변」은 탭이 아니라 홈의 **버튼과 정렬 기준**으로 흡수된다. 레퍼런스도 같은 판단을 했다. 「혼잡예보」는 원래도 탭이 아니었다 — `handleTab`이 `'forecast'`를 무시하고 있었고, 명소를 골라야 성립하는 상세라 단독 진입점이 없다. 새 구조에서 자연히 인플레이스 상세가 된다.

**「혼잡예보」라는 이름이 화면에서 사라진다.** README·PLAN의 "화면 넷" 서술을 함께 고친다.

목록 정렬은 **거리순 · 여유한 순 · 붐비는 순** 셋이다. 지금은 거리순·혼잡도순 둘뿐이라 `SortSelect`가 토글 버튼 하나인데(시안의 드롭다운을 "선택지가 둘뿐이라 메뉴를 여는 탭 한 번이 낭비"라고 판단해 바꾼 것), 셋이 되면 토글로는 표현되지 않으므로 **분절 컨트롤(segmented control)로 바꾼다.** 「붐비는 순」을 더하는 이유는 「지금 핫플」 프리셋과 「오늘의 서울」의 붐빔 TOP이 같은 관심사를 이미 다루고 있어서다. 위치가 없으면 거리순은 비활성이고 기본값이 여유한 순으로 떨어진다 — 현재 폴백 규칙 그대로다.

레퍼런스에 있는 **「가나다」 정렬은 넣지 않는다.** 30곳에서는 이름으로 찾을 일이 검색으로 해결되고, 이름순이 값을 하는 것은 목록이 길어지는 121곳부터다.

### 2.4 「더보기」는 「오늘의 서울」이 된다

도시 정보가 상세로 내려가면서 탭 하나가 통째로 빈다. 빈 탭에 설정만 넣으면 하루에 한 번도 안 열리는 탭이 된다.

지도가 **공간적 조망**을 준다면 여기는 **전체 조망**을 준다. "30곳 중 붐빔 5곳" 같은 건 지도를 아무리 봐도 안 보인다. 구성은 혼잡도 분포 한 줄, 붐비는 곳·여유로운 곳 TOP, 카테고리별 평균 혼잡도, 재난문자 모음, 「가까우면서 여유로운 곳」 추천, 맨 아래 데이터 출처와 설정이다.

**추가 API 호출이 0이다.** 이미 받는 30곳 스냅샷을 다르게 집계할 뿐이다. 화면을 하나 늘리면서 쿼터를 건드리지 않는다는 점이 이 선택의 가장 큰 근거다.

갈 곳을 잃은 「가까우면서 여유로운 곳」 추천 캐러셀(`RecommendationCard`)도 여기로 옮긴다.

### 2.5 카테고리를 공식 5종으로 — 30곳에서는 손해를 감수한다

현행 분류(`공원`·`쇼핑몰`·`카페`·`문화재`·`기타`)를 서울시 공식 분류로 바꾼다. 출처는 저장소의 `실시간 도시데이터 매뉴얼.pdf` p9~10 「주요장소 목록」이다.

| 공식 분류 | 121곳 | 우리 30곳 | 화면 라벨 |
|---|---|---|---|
| 인구밀집지역 | 48 | 2 | 역·번화가 |
| 공원 | 33 | 10 | 공원 |
| 발달상권 | 28 | 12 | 상권·거리 |
| 관광특구 | 7 | 3 | 관광특구 |
| 고궁·문화유산 | 5 | 3 | 고궁·유적 |

30곳 전부가 공식 목록에 매칭됨을 스크립트로 확인했다. 재분류 결과:

- **「기타」 7곳이 사라진다.** 명동·이태원·잠실 관광특구는 이름에 관광특구가 들어 있는데도 「기타」였다. 강남역·홍대입구역(2호선)은 인구밀집지역이 된다.
- **「문화재」 6곳이 갈라진다.** 경복궁·광화문·덕수궁·창덕궁·종묘는 고궁·문화유산으로, 북촌한옥마을·인사동·서촌은 **발달상권**으로 간다.
- 「카페」 3곳과 「쇼핑몰」 4곳은 전부 발달상권으로 합쳐진다.

**30곳 구간에서는 이 교체가 손해다.** 현행 분포는 10/7/6/4/3으로 고른데 공식은 12/10/3/3/2로 쏠린다. 「역·번화가」는 2곳짜리 칩이라 거의 죽은 칩이고, 「기타」 7곳 문제가 「상권·거리」 12곳 문제로 옮겨갈 뿐이다.

그럼에도 교체하는 이유는 **121곳이 목표이기 때문**이다. 121곳에서는 48/33/28/7/5로 균형이 잡히고, 무엇보다 매뉴얼에 카테고리가 이미 붙어 있어 확장할 때 좌표만 채우면 된다. 현행 분류를 유지하면 121곳을 손으로 다시 분류해야 하고, 그 작업은 「카페」와 「쇼핑몰」의 경계를 91곳에 대해 사람이 판정하는 일이 된다.

**즉 30곳 구간의 쏠림은 임시 비용이다.** 다음 세션이 "칩 분포가 이상하다"며 되돌리지 않도록 여기 적어 둔다.

화면 라벨을 따로 두는 이유는 「인구밀집지역」·「발달상권」이 행정 용어라서다. 데이터는 공식 값을 갖고 표시만 바꾼다.

### 2.6 프리셋을 카테고리에서 떼어낸다

「데이트」가 깨진다. 현행 정의는 `카페 ∪ 문화재 ∪ 공원`(19곳)인데 공식 분류에 「카페」가 없다. 그대로 옮기면 `고궁·유적 ∪ 공원 ∪ 상권·거리` = **30곳 중 25곳**이 되어 필터가 아니게 된다.

원인은 축이 다르기 때문이다. 공식 분류는 "어떤 성격의 구역인가"이고 프리셋은 "거기서 뭘 하려는가"이다. 광장(전통)시장과 청담동 명품거리가 같은 「상권·거리」인데 데이트 적합성은 정반대다.

카탈로그에 목적 태그를 독립 필드로 둔다.

```ts
readonly category: AreaCategory          // 공식 5종. 필터 칩용
readonly purposes?: readonly Purpose[]   // 'kids' | 'date'. 프리셋용
```

프리셋 정의는 `purposes` + 실시간 혼잡도가 된다. 「지금 핫플」은 원래 혼잡도만 보므로 그대로다. 121곳으로 늘 때 태그가 없는 명소는 나들이·데이트에 걸리지 않고 핫플에는 걸린다 — **빈 값이 조용히 오분류되지 않고 그냥 빠진다.**

목적 프리셋 설계 §3의 "카테고리와 혼잡도를 함께 쓴다"는 판단은 카테고리가 활동 축이었을 때 맞았다. 축이 구역 성격으로 바뀌면서 전제가 사라졌다.

### 2.7 즐겨찾기는 기기에 저장한다

`src/platform/favorites.ts`가 앱인토스 스토리지를 먼저 쓰고 없으면 `localStorage`로 폴백한다. `links.ts`가 이미 쓰는 패턴이고, 브리지가 없는 개발 서버·jsdom에서 동작해야 테스트가 된다.

서버 저장을 기각한 이유는 PLAN.md가 "무료고 로그인도 없다"고 정해둔 것이다. 로그인이 없으면 익명 기기 ID를 발급·보관해야 하고, 지금 `api/`는 상태를 갖지 않는 순수 중계기라 DB가 새로 들어온다. 기기를 바꾸면 즐겨찾기가 사라지는 것은 이 선택의 알려진 대가다.

### 2.8 도시 정보는 접어두고 펼칠 때 부른다

상세에 도시 정보가 들어가면 호출 시점이 바뀐다. 지금은 사용자가 「더보기」 탭을 열 때만 `/api/cityinfo`를 부르는데, 앞으로는 명소를 누를 때마다 부를 수 있다.

CDN 캐시가 명소·TTL 단위로 묶으므로 **최악은 여전히 30곳 × 24 = 720회/일로 같다.** 달라지는 것은 그 최악에 도달할 확률이다. 혼잡도 720회와 합치면 1,440회로 하루 1,000회를 넘는다(STATE.md "더보기는 호출량을 늘린다").

그래서 「이곳의 도시 정보」 섹션을 **접힌 상태로** 두고 펼칠 때 조회한다. 탭 한 번이 늘지만, `cityInfoSchema.ts` 머리말과 STATE.md가 도시 정보를 "부가 정보"로 규정하고 있어 성격에 맞는다. 손잡이는 여전히 `CITYINFO_CACHE_TTL_SECONDS`이고, 활용갤러리 등록으로 한도가 풀리면 이 결정은 되돌려도 된다.

## 3. 레이어 배치

기존 레이어 규칙(AGENTS.md)을 그대로 따른다. 도메인은 React를 모르고, 컴포넌트는 props만 받고, 화면이 데이터를 가져온다.

### 3.1 `src/domain/`

### 3.5 상태 배치

**`App.tsx`는 탭만 든다.** 선택된 명소·검색어·카테고리·프리셋·정렬·분할 비율은 전부 `HomeScreen` 안에 둔다. 지금은 `App.tsx`가 `selectedArea`를 들고 있어 지도 상태가 셸로 새어나갔는데, 홈이 언마운트되지 않으므로 올릴 이유가 없어진다.

필터 상태가 여섯이라 `useHomeFilters` 훅 하나로 묶는다. `HomeScreen`은 조립만 남는다. 현재 최대 파일이 `MapScreen.tsx` 203줄이므로 AGENTS.md의 200~400줄 기준 안에서 유지할 수 있다.

## 4. 에러 처리

| 상황 | 처리 |
|---|---|
| 지도 키 없음 / 스크립트 로드 실패 | **지도 영역만** `MapUnavailableNotice`로 바꾼다. 검색·필터·목록·상세는 정상 동작한다. 분할 손잡이는 지도를 최소로 접는다 |
| 즐겨찾기 저장 실패 | 조용히 메모리 유지. 별은 정상 표시. 부가 기능이라 화면을 막지 않는다 |
| 즐겨찾기 읽기 실패 | 빈 목록으로 떨어뜨리되 `console.error`로 남긴다. "저장된 게 없음"과 구분한다 |
| 검색 0건 | 찾은 말을 되돌려 보여준다 — "「성수」로 찾은 명소가 없어요" |
| 프리셋 0건 | 기존 처리 유지 — 칩에 개수를 달고 0이면 비활성 |
| 도시 정보 실패 | 접힌 섹션을 펼쳤을 때만 드러난다. 상세의 나머지는 유지한다 |
| 위치 권한 없음 | 기존 처리 유지 — 거리순 대신 혼잡도순, 상단 안내 |

지도 키 없음이 가장 중요하다. 지금은 지도가 독립 탭이라 실패해도 「내 주변」이 멀쩡했는데, 이제 지도가 홈의 절반이다. 이게 깨지면 키 하나 없다고 앱 전체를 못 쓴다.

## 7. 미해결 가정

- **드래그 손잡이와 지도 팬 제스처가 토스 웹뷰에서 충돌하는지 확인되지 않았다.** jsdom에서 포인터 이벤트 합성으로 로직은 고정하지만, 실제 충돌은 실기기로만 안다. 걸리면 손잡이 영역을 지도 밖으로 완전히 분리하거나 고정 분할로 후퇴한다.
- **상시 레이아웃 시트가 심사에 걸리는지 확정하지 못했다.** 이번 설계는 시트를 아예 쓰지 않아 이 위험을 피했지만, 판단 근거 자체는 여전히 미확인이다.
- **30곳 구간의 카테고리 쏠림이 사용자에게 얼마나 불편한지 모른다.** 「역·번화가」 2곳 칩이 실제로 거슬리는지는 써봐야 안다. 121곳 확장 전까지는 감수한다.
- **목적 태그의 내용이 사용자 기대와 맞는지 확인되지 않았다.** 목적 프리셋 설계 §8의 열린 질문이 그대로 남는다 — 태그를 손으로 붙이는 방식으로 바뀌었을 뿐 판단 근거는 여전히 가정이다.
- **매뉴얼 PDF에서 추출한 카테고리의 공백 처리.** 이름 대조와 같은 문제가 남는다(`areas.test.ts`의 `it.todo`). 30곳은 전부 매칭됐으므로 이번 범위에서는 문제가 없다.
